Results

Measured, not claimed

Every number on this page comes from a real end-to-end run of the pipeline. The run script writes them to site/data/run_metrics.json, and this page reads that file. Run it again and the page changes.

How fast is an alert raised?

In one sentence: about 20 seconds from a payment being saved in the bank's database to a fraud alert being written, against next day today.

Each dot is one alert. Its value is the time between the source database saving the last payment behind the alert and the alert being written (latency). Here the pipeline ran straight after each batch of activity, so this is pure processing time. On Databricks the job runs every 5 minutes, which adds up to 5 minutes of waiting. That is still minutes instead of a day (T+1). p50 / p95 are in the tiles above.

Are the alerts right?

In one sentence: every planted fraud case was caught; two rules raised no false alarms, and the third raises some on customers who are travelling.

The data generator plants fraud on purpose and keeps a private list of it (the ground truth), which never reaches the bank's systems. Comparing alerts with that list gives two scores: precision (how many alerts were real fraud) and recall (how much fraud was caught).

The impossible-travel rule's false positives are real customers starting or ending a trip: a last purchase in Lisbon and a first one in Madrid within the hour. A production rule would use the distance and minimum travel time between countries. One planted case can also raise two alerts (going out and coming back), which is why "true positives" can be higher than "planted".

What was captured

Every change event published, by source table and type of change. Card payments get many updates (authorised, then settled or reversed), and a few expired authorisations are deleted.

How long each step takes

Round 0 loads the starting customers and accounts. Each later round is one simulated hour of bank activity, processed end to end. This ran on a small 4-core machine; a Databricks cluster would be faster, but the shape is what matters: each step's time stays flat as data grows, because each run only processes what is new.

Did anything go missing?

In one sentence: no. After every round, the copy matched the source row for row and to the cent.

Reconciliation checks from the last round. Row counts and balance totals are compared between the source and the Silver copy, and every event Kafka confirmed is checked against Bronze. The job fails on any mismatch, so a finished run means these held after every round.
