Decisions

The choices behind the design, and what each one costs

Each decision is written up as a short record (ADR): the situation, what was chosen, and the price paid.

ADR-001 · Changes are captured inside Databricks, not by a separate tool

Situation. The usual open-source setup uses a separate tool (Debezium) to push database changes into Kafka, and Databricks only reads them. The target platform works the other way round: Databricks itself watches the sources and publishes to Kafka.

Decision. Capture is written as small Python adapters run from Databricks notebooks, with bookmarks and audit records stored in Delta.

Cost and benefit. One platform to run, one place for access control and lineage (Unity Catalog), and it handles sources Debezium can't, like a shared folder of files. The price: changes are collected on a schedule rather than the instant they happen, and the capture code is ours to maintain.

ADR-002 · Duplicates are allowed in transit, removed on arrival

Decision. No Kafka transactions. Instead: Kafka confirms every message (acks=all), the bookmark moves only after that confirmation, every change carries an ID derived from the change itself, Bronze drops repeated IDs, and Silver ignores anything older than what it holds.

Why. Kafka transactions wouldn't cover the Delta writes anyway. Making every step safe to repeat (idempotent) is simpler to reason about and to test.

Cost. Any other consumer of the topics must also drop repeated IDs. That is part of the documented data contract.

ADR-003 · Partner files are tracked with a file list, not Auto Loader

Auto Loader can't read an Azure File Share. Copying files to a supported storage first would work, but adds a step where files can go missing. The pipeline reads the share directly and records every file version it has processed (name, ETag, fingerprint), so a corrected file sent again is recognised as an update.

ADR-004 · Deleted rows are flagged, not removed

A delete sets a flag (soft delete). This stops a late, older insert from bringing a deleted row back, and keeps evidence for the fraud rules: a cancelled card payment is still an attempt. Anyone wanting only current rows filters on the flag, as reconciliation does.

ADR-005 · Event format checked in tests now, Schema Registry next

Events are JSON, and the tests check every adapter's output against a published JSON Schema. The production step is registering that format in Confluent's Schema Registry, so Kafka itself rejects a change that would break consumers.

ADR-006 · Kafka topics are created on purpose, never automatically

Automatic topic creation is switched off. The pipeline creates any missing topics with a fixed number of partitions before reading. That way a table with no changes yet can't break the pipeline, and every topic name is a deliberate choice.

ADR-007 · Built and measured locally, deployed to the cloud in short runs

Databricks' free edition limits internet access, and Confluent Cloud's free credit expires after about a month. Everything is therefore built and tested on a laptop-sized setup (Docker: SQL Server and Kafka, plus local Spark and Delta), then deployed with the Asset Bundle for short cloud runs.
