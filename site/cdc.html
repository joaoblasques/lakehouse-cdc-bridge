CDC patterns

Each source gets the CDC technique it can actually support

A bank's sources don't all expose a transaction log you can read. Picking the technique per source, and knowing what each one misses, is most of the work. Every adapter emits the same event envelope, so nothing downstream needs to know which technique produced it.

SQL Server: log-based CDC

SQL Server Agent's capture job reads the transaction log into cdc.<schema>_<table>_CT tables. The adapter reads them between the last LSN it processed (the watermark, stored in Delta) and the current maximum LSN:

SELECT sys.fn_cdc_map_lsn_to_time(__$start_lsn) AS __commit_ts, *
FROM cdc.fn_cdc_get_all_changes_dbo_accounts(@from_lsn, @to_lsn,
                                             N'all update old')
ORDER BY __$start_lsn, __$seqval, __$operation

all update old returns the before image (operation 3) and after image (operation 4) of each update. The adapter pairs them on (start_lsn, seqval) into one u event.

What can go wrong, and how it's handled

  • Retention cleanup outruns the pipeline. If the stored LSN is older than sys.fn_cdc_get_min_lsn(), changes were purged before they were read. The adapter raises CdcGapError instead of skipping them, so the table gets re-snapshotted.
  • Capture job lag. A heartbeat table, also CDC-enabled, is written after each batch. Its arrival in the change table measures how far the Agent job is behind.
  • Money precision. DECIMAL(18,2) is carried as a string in the event and parsed back to DECIMAL(18,2) in Silver. It never passes through a float.
  • Order. The Kafka key is table:primary key, so every change to one row lands on one partition, in LSN order.

Azure File Share: file-arrival CDC

Auto Loader cannot read Azure Files. It supports ADLS, Blob storage and Unity Catalog volumes; Azure Files is an SMB share. So the adapter lists the share through the storage SDK and compares each file's (name, etag) with what it has already processed:

  • New file → one c event per row.
  • Same name, new etag (partner re-sent a corrected file) → u events. Silver upserts on transfer_id.
  • Unchanged → skipped.

Each event's position is file:line@sha256, so an auditor can locate the exact line in the exact version of the file.

Bad rows go to the DLQ, not the floor

Each row is validated before it becomes an event: required fields, amount format, IBAN mod-97 check. A partner who sends 1.250,00 (European format) produces a message on banking.cdc.dlq with the reason, file and line. The file manifest records how many rows were rejected, so the gap is visible in Delta, not just in the logs.

{"source_system": "azure_fileshare",
 "position": "sepa_partner_20261001_1000.csv:14@3fa1…",
 "reason": "invalid amount",
 "raw": {"amount": "1.250,00", …}}

The event envelope

Every adapter emits this shape (JSON Schema in schemas/change_event.schema.json).

{
  "event_id": "sha256(system|table|key|position)",   // deterministic: replays dedupe
  "op": "u",                                         // c | u | d | r
  "key":    {"account_id": 42},
  "before": {"account_id": 42, "balance": "1520.30", …},
  "after":  {"account_id": 42, "balance": "1488.10", …},
  "source": {
    "system": "sqlserver", "database": "cards", "table": "dbo.accounts",
    "position": "0x0000002c000004b80003:0x0000002c000004b80002",
    "commit_ts": "2026-10-01T10:14:03.217",
    "sequence": null                                 // files: "mtime|name|line"
  },
  "captured_at": "2026-10-01T10:14:06.880+00:00",
  "trace_id": "one per capture run",
  "payload_hash": "sha256(before, after)",
  "schema_version": 1
}

DB2 and SingleStore (phase 2)

DB2: when you can't read the log

Reading DB2's log needs IBM InfoSphere CDC or Q Replication, which a consuming team often isn't allowed to install on a production mainframe. The fallback is a ROW CHANGE TIMESTAMP column as the watermark, which catches inserts and updates. It misses hard deletes, so a periodic snapshot hash diff (key plus row hash, compared with the previous snapshot) emits the deletes. The trade-off is latency and MIPS cost against completeness, and the scan frequency is a business decision.

SingleStore

SingleStore has native log-based CDC through OBSERVE, but the free Shared edition does not support CDC pipelines. The MVP plan is a watermark on an updated_at column plus a row hash, with OBSERVE recorded in an ADR as the production choice on a Standard or Enterprise workspace.
