CDC patterns

Each source system needs its own way of spotting changes

Some databases let you read their internal record of changes. Others don't, and some sources are just folders of files. So each source gets the change data capture technique it can support. They all produce the same event format, so nothing downstream needs to know which technique was used.

SQL Server: reading the change log

In one sentence: SQL Server already records every change it makes, and the pipeline reads that record from where it left off last time.

How it works

  1. Every database keeps a transaction log. With CDC switched on, SQL Server's capture job copies each change from that log into a readable change table.
  2. Each change has a position number, its LSN, and positions only go up.
  3. The pipeline remembers the last LSN it handled (its watermark) and asks SQL Server for everything after it.
  4. An update arrives as two rows, "before" and "after". The pipeline joins them into one event, so consumers see what changed.
-- every change to accounts between two log positions
SELECT * FROM cdc.fn_cdc_get_all_changes_dbo_accounts(
         @from_lsn, @to_lsn, N'all update old')

What can go wrong, and how it is handled

  • The pipeline is down too long. SQL Server deletes old changes after a few days (retention). If the bookmark is older than the oldest change still kept, the pipeline stops with an error instead of silently skipping the gap.
  • The capture job falls behind. The pipeline writes a heartbeat row and times how long it takes to come back through CDC.
  • Money gets rounded. Amounts travel as exact text ("1520.30"), never as floating-point numbers, so no cent is lost.
  • Changes arrive out of order. Each event's Kafka key is the row's ID, so all changes to one account stay in one partition, in order.

Partner files: spotting new and changed files

In one sentence: the pipeline lists the shared folder, compares it with the files it has already processed, and turns each row of every new file into an event.

How it works

Databricks' usual file tool, Auto Loader, can't read an Azure File Share. So the pipeline reads the share directly and keeps a list of every file it has processed, with the file's version tag (ETag) and fingerprint (SHA-256 hash).

  • New file: each row becomes an "insert" event.
  • Same file name, new content (the partner re-sent a corrected file): its rows become "update" events.
  • Unchanged file: skipped.

Each event records its file, line number and file fingerprint, so an auditor can find the exact line in the exact version of the file.

Bad rows are set aside, not lost

Each row is checked before it becomes an event: required fields present, amount readable, and account numbers valid (IBAN check digits). A row that fails goes to the dead-letter queue with the reason. For example, a partner writing an amount the European way:

{"position": "sepa_partner_20261001_1000.csv:14@3fa1…",
 "reason":   "invalid amount",
 "raw":      {"amount": "1.250,00", …}}

The file list also records how many rows were rejected, so the gap is visible in the data, not just in the logs.

The event format every source uses

One envelope for every change, written down as a JSON Schema (schemas/change_event.schema.json) and checked by the tests. This is the project's data contract.

{
  "event_id": "…",          // fingerprint of source + table + row + position: same change, same ID
  "op": "u",                // c = insert, u = update, d = delete
  "key":    {"account_id": 42},
  "before": {"balance": "1520.30", …},    // the row before the change
  "after":  {"balance": "1488.10", …},    // the row after the change
  "source": {
    "system": "sqlserver", "table": "dbo.accounts",
    "position": "0x0000002c…:0x0000002c…",  // LSN, or file:line@fingerprint for files
    "commit_ts": "2026-10-01T10:14:03.217"  // when the source saved it
  },
  "captured_at": "2026-10-01T10:14:06.880+00:00",
  "trace_id": "…"           // one per capture run, to group a run's events
}

Next: DB2 and SingleStore

DB2: when you can't read the log

Reading a mainframe's change log needs IBM tools that a downstream team usually isn't allowed to install. The fallback is to ask for rows whose "last changed" timestamp is newer than the bookmark (query-based CDC). That misses deleted rows, so a periodic full comparison (snapshot hash diff) catches them. The trade-off: more frequent comparisons find deletes sooner but cost more mainframe time (MIPS). How often to run them is a business decision.

SingleStore

SingleStore has a native change feed (OBSERVE), but the free tier doesn't support it. The plan is the same timestamp-plus-comparison approach as DB2, with the native feed documented as the production choice on a paid tier.
