Architecture

How a change travels from the bank's database to a fraud alert

Databricks does the watching: small programs check each source system for changes and publish them to Kafka. Everything downstream, including this project's own tables and alerts, reads from Kafka and never touches the source systems.

Follow one card payment

  1. A customer pays with a card. The cards system (SQL Server) saves the payment. SQL Server also writes it to its transaction log, and its capture job copies it into a change table within seconds.
  2. The capture step picks it up. A Databricks notebook reads every change since its last bookmark, wraps each one in the standard event format, and gives it an ID that never changes.
  3. It is published to Kafka. The event goes to the card-transactions topic. Kafka confirms it is stored (acks=all), and only then does the pipeline record where it landed (audit trail) and move its bookmark forward.
  4. It lands in Bronze. A Spark job copies new Kafka events into the raw Bronze table, dropping any duplicate with the same ID.
  5. Silver is updated. The payment's current state (authorised, then settled) is applied to the Silver table with a MERGE. An older change can never overwrite a newer one (ordering guard).
  6. The fraud rules run. If this is the fifth payment on the account in ten minutes, the velocity rule writes an alert to Gold, well under a minute after the payment was saved.
  7. The alert reaches an analyst. Gold publishes new alerts to Kafka (outbox pattern). The fraud-alert service reads them and puts each one in the analysts' queue, where someone confirms the fraud or dismisses the alert.
  8. Everything is checked. Reconciliation compares counts and balance totals with the source. If anything is missing, the job fails loudly.

The whole picture

The scheduled job

All steps run as one Databricks Workflows job, defined in databricks.yml (an Asset Bundle). It runs every five minutes, and never twice at the same time, because each source's bookmark must have a single writer.

capture  (runs once per source: SQL Server, file share, DB2)
   └─ bronze ─ silver ─┬─ gold        (fraud alerts)
                       └─ reconcile   (fails the run if anything is missing)

The capture step is a for-each task: the same notebook runs once for each source listed in conf/sources.yml.

Design choices that matter

Duplicates are harmless

Every change gets an ID built from where it came from (deterministic event ID). If a crash makes the pipeline send a change twice, both copies have the same ID and Bronze keeps only one. Kafka may deliver twice, but each change takes effect once in Delta (at-least-once, exactly-once).

The bookmark moves last

The order is always: send to Kafka → wait for confirmation → record the audit row → move the watermark. If any step fails, the bookmark stays put and the next run resends the same changes. Data can be sent twice, but never skipped.

Old changes can't undo new ones

Silver only accepts a change if it is newer than what it already holds, using the database's own order (LSN) or, for files, the file time and line number. A late or replayed change can't roll a balance back.

Deleted rows are kept, flagged

A delete marks the row as deleted (soft delete) instead of removing it. That keeps the evidence: a cancelled card payment still counts as an attempt for the fraud rules.

New tables are configuration, not code

Sources, tables, keys and topics are listed in one configuration file. A new source type needs one new adapter; everything after capture stays the same.

No passwords in the code

On Databricks, credentials come from a secret scope; locally, from environment variables. With a Confluent API key present, the connection switches to an encrypted login (SASL_SSL) automatically.

The fraud-alert service

In one sentence: a small web service that receives every new alert from Kafka and gives fraud analysts a queue to work through.

How alerts get there

  • Gold publishes with an outbox. Each alert row has a "published" time, empty at first. The publish step sends only empty ones, waits for Kafka to confirm (acks=all), then fills the time in. A crash in between means the alert is sent again, never lost.
  • The service stores before it confirms. It tells Kafka it has read a message (commits the offset) only after saving the alert. If it stops in between, Kafka sends the alert again.
  • Sending twice is harmless. Alerts are saved by their ID (idempotent), so a repeat only refreshes the evidence. An analyst's decision is never overwritten.
  • One account, one order. Alerts use the account as their Kafka key, so an account's alerts arrive in order.

What analysts can do (REST API)

GET   /alerts?status=OPEN&rule=card_velocity
GET   /alerts/{alert_id}
PATCH /alerts/{alert_id}   {"status": "CONFIRMED", "note": "card blocked"}
GET   /stats               counts by rule and status
GET   /health
GET   /docs                interactive API documentation

Built with FastAPI. It runs in its own 255 MB Docker image, without Spark or database drivers, as a non-root user. The store is SQLite, behind a small class, so a production database would not change the API.
