AI onboarding

An AI assistant drafts the config for a new table, and a person approves it

Adding a table to the pipeline used to mean writing its configuration by hand. Now a language model (LLM) writes a first draft from the table definition. Code checks that draft against the facts, and an engineer approves it.

The problem

Each new source table needs an entry in conf/sources.yml. To write it, someone reads the table definition (DDL) and works out:

  • the primary key, and for DB2 the timestamp column to poll;
  • a Kafka topic name and a Silver table name that follow the existing pattern;
  • the Silver schema, one Spark type for each column;
  • which columns hold personal data (PII), such as names, tax numbers and IBANs, and how to protect them.

Done by hand, this is slow, and small mistakes are easy to make. A key column with a typo, or a missed tax number column, only shows up later, in production.

How it works

  1. Give it the DDL. One CREATE TABLE statement from DB2 or SQL Server, and the name of the source it belongs to.
  2. Claude drafts the judgment parts. The key, the topic name, the Silver table name, which columns are personal data and how to handle each one, plus review notes such as "this rate is stored as a floating-point number".
  3. Code checks every claim. Does each key column exist? Does it match the key the DDL declares? Is the DB2 watermark really a TIMESTAMP? Are the names new, and do they follow the pattern? Does every column marked as personal data exist? Can every type be mapped to Spark?
  4. A proposal file is written. It goes to conf/proposals/ and holds the entry, the checker's findings, the model's notes, and where the draft came from.
  5. A person approves it. An engineer reads the proposal, copies the entry into conf/sources.yml and opens a pull request. That pull request is the approval.

Who decides what

The model: judgment

Naming, spotting personal data, and the risks a careful reviewer would flag. These are the parts a person would otherwise think through.

The code: facts

Columns, types and keys come from parsing the DDL. The Silver schema is built from the DDL, never taken from the model. Every column name in the model's answer is checked against the real list.

A person: approval

Nothing reaches conf/sources.yml until an engineer has read it and merged a pull request (human in the loop).

Safety choices

ChoiceWhy
Only the table definition is sent, never rowsNo customer data leaves the bank. The model sees column names and types, nothing more.
The DDL is treated as dataA column comment could contain text like "ignore your instructions". The prompt marks the DDL as material to analyse, not orders to follow, as a guard against prompt injection.
Answers must fit a fixed formatThe model must reply in a set JSON shape (structured output), so the code never has to guess what a sentence meant.
A refusal or a cut-off answer is an errorIf the model declines, or its answer stops part-way, the tool stops with a clear error. It never tries to use half an answer.
Server-side fallbackIf the main model is busy, the API can answer with another model instead of failing. The proposal records which model actually answered.
Provenance in the fileEach proposal records the model, the message ID and a SHA-256 fingerprint of the DDL. A reviewer can see which definition the draft was made from.

Example: DB2 term deposits

NOT A REAL RUN This example shows the format of a proposal. It has not been produced by the live model yet, because no API key was available when this was built. The model's part (summary, personal data, notes) was written by hand, as in the automated tests. The rest was produced by the real code from the DDL below.

Input: tests/fixtures/ddl/db2_deposits.sql, a trimmed DB2 table of term deposits with a holder name, a tax number (NIF), an IBAN and a rate stored as DOUBLE.

CREATE TABLE "CORE"."DEPOSITS" (
  "DEPOSIT_ID"    INTEGER NOT NULL,
  "HOLDER_NAME"   VARCHAR(120),
  "HOLDER_NIF"    CHAR(9),
  "IBAN"          VARCHAR(34) NOT NULL,
  "PRINCIPAL"     DECIMAL(18, 2) NOT NULL,
  "BONUS_RATE"    DOUBLE,
  ...
  "ROW_CHANGED"   TIMESTAMP NOT NULL GENERATED ALWAYS FOR EACH ROW ON UPDATE
                  AS ROW CHANGE TIMESTAMP IMPLICITLY HIDDEN,
  CONSTRAINT "PK_DEPOSITS" PRIMARY KEY ("DEPOSIT_ID")
);

Output: conf/proposals/db2_core__CORE.DEPOSITS.yml

status: ready_for_review
source: db2_core
entry:                              # goes into conf/sources.yml after review
  schema: CORE
  table: DEPOSITS
  primary_key: [DEPOSIT_ID]         # checked against the declared key
  ts_column: ROW_CHANGED            # checked: a TIMESTAMP that DB2 maintains
  topic: banking.cdc.core.deposits
  silver_table: silver_deposits
  silver_schema: DEPOSIT_ID INT, CUSTOMER_ID INT, HOLDER_NAME STRING,
    HOLDER_NIF STRING, IBAN STRING, PRINCIPAL DECIMAL(18,2), RATE_PCT DECIMAL(5,3),
    BONUS_RATE DOUBLE, OPENED_ON DATE, MATURES_ON DATE, STATUS STRING   # from the DDL
review:
  summary: Term deposits held by customers.
  validator: []                     # no errors found by the code
  model_notes:
  - severity: warning
    note: BONUS_RATE is DOUBLE; rates should be DECIMAL.
  pii_columns:
  - {column: HOLDER_NAME, category: name, handling: mask}
  - {column: HOLDER_NIF, category: tax_id, handling: hash}
  - {column: IBAN, category: account_number, handling: keep_restricted}
provenance:
  model: claude-opus-5-5
  message_id: msg_...
  generated_at: '2026-10-01T17:46:01+00:00'
  ddl_sha256: 7d195ab1...e687e27

If the checker finds an error, or the model marks something as a blocker, the status is needs_changes and the command exits with code 1. The file is still written, so the reviewer can see why.

How to run it

  1. Install the optional AI package. 
    uv sync --extra ai
  2. Set your API key in the shell. Do not put it in a file in the repository. 
    export ANTHROPIC_API_KEY=...
  3. See the prompt first, without calling the model: 
    uv run python -m banking_cdc.onboarding \
  --ddl tests/fixtures/ddl/db2_deposits.sql --source db2_core --dry-run
  4. Draft the entry. 
    uv run python -m banking_cdc.onboarding \
  --ddl tests/fixtures/ddl/db2_deposits.sql --source db2_core
    Result: the command prints the status and the path of the proposal file.
The automated tests replace the model with a fake. They prove what the code does with any answer it gets: they check the parsing, the checker and the file format. They do not judge how good the model's answers are. That is the reviewer's job, and the reason a person approves every entry. See ADR-010 for the reasoning.
